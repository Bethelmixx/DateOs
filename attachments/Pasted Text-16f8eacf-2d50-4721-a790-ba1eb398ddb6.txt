=== 1. Rate limiting en login/signup (CRÍTICO) ===
Archivo: src/lib/auth/server.ts

Agregá `rateLimit` a la config de `betterAuth({...})`:
- enabled: true (no confiar en el default por NODE_ENV)
- storage: "database" — OBLIGATORIO en Vercel: el storage en memoria
  (default de better-auth) NO sirve acá porque cada invocación
  serverless puede ser una instancia nueva sin memoria compartida; sin
  esto el rate limit sería casi decorativo en producción.
- modelName: "rateLimit" (default, dejalo explícito)
- customRules como OBJETO (no array) keyeado por path, ej:
    customRules: {
      "/sign-in/email": { window: 10, max: 5 },
      "/sign-up/email": { window: 60, max: 3 },
    }

NO agregues `advanced.ipAddress.ipAddressHeaders` ni `trustedProxies`.
En Vercel el header default que usa better-auth (x-forwarded-for) ya es
confiable tal cual: Vercel lo sobreescribe con la IP real del cliente y
NO deja pasar un x-forwarded-for falsificado desde afuera (salvo que
haya un proxy propio delante de Vercel, que acá no lo hay). Agregar esa
config sería trabajo de más y no cambia nada.

Esto requiere una tabla nueva. Agregá una migración
migrations/0003_rate_limit.sql siguiendo el estilo de
migrations/0001_auth.sql (columnas camelCase entre comillas dobles):

  create table if not exists "rateLimit" (
    "id" text primary key not null,
    "key" text,
    "count" integer,
    "lastRequest" bigint
  );

Como scripts/migrate.mjs y src/lib/db.ts ya leen todo migrations/*.sql
automáticamente, no hace falta tocar nada más para que esto se aplique
solo en el próximo deploy de Vercel. Antes de aplicar: confirmá contra
la versión instalada de better-auth (package.json dice ~1.6.30) que el
nombre de tabla/columnas no cambió.

Nota aparte (no es código, es config de Vercel/Neon — solo avisame si
la ves mal): en el dashboard de Vercel, DATABASE_URL debería apuntar al
endpoint "pooled" de Neon (el host suele tener "-pooler" en el nombre).
Con storage:"database" el rate limiter va a pegarle a Postgres en cada
intento de login/signup, y en serverless sin pooling se puede agotar el
límite de conexiones directas de Neon bajo concurrencia. Si ves que
DATABASE_URL no es el pooled, decímelo en vez de cambiarlo vos.

=== 2. Validar que photoData/avatarUrl sean imágenes reales (ALTO) ===
Archivos: src/lib/reports/server.ts (createReport validator) y
src/lib/profiles/server.ts (updateMyProfile validator)

Hoy solo se valida el tamaño (380_000 chars). Agregá una validación de
formato antes de aceptar el dato: debe matchear
  /^data:image\/(jpeg|png|webp);base64,[A-Za-z0-9+/]+=*$/
y el payload base64 decodificado no debe superar ~280KB reales (el
límite actual es sobre el string completo con el prefijo data URL, dejá
margen). Si no matchea, rechazar con un error claro en español, mismo
estilo que los otros throw new Error(...) de esos archivos.
